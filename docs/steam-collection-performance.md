# Steam 수집 성능 측정

측정일: 2026-10-10. 기존 코드는 `0f26745`의 `src/server/activity/steam-facts.ts`, 개선 코드는 같은 함수의 일괄 조회·저장 버전이다.

## 측정 방법

일회성 로컬 PostgreSQL 17 컨테이너에 실제 마이그레이션을 적용했다. Node.js 24에서 Vitest로 실제 저장 함수를 실행하고, `PoolClient.query` 호출 수와 함수 전체 실행 시간을 측정했다. Steam API 호출·계정 생성·초기 데이터 준비·DB 연결 획득 시간은 측정에서 제외했다. 각 경우마다 1회 준비 실행 후 5회를 측정했으며 아래 시간은 중앙값이다. 경우별로 기존 함수를 먼저, 개선 함수를 다음에 실행했다. 순서를 무작위화한 부하 실험은 아니다.

테스트 계정은 확인 정보와 활성 수집 요청을 가진다. 게임은 ID 1000부터 1999까지 1,000개, 기준 누적 시간은 100분이다. 첫 저장은 빈 기준 테이블에서 시작하고, 증가분 저장은 모든 게임이 120분으로 증가한 다음 관측, 변화 없음은 모든 게임이 100분인 다음 관측이다. 각 실행 전에 계정의 기준값과 증가분을 초기화했다. 실제 사용자 데이터나 운영 DB는 사용하지 않았다.

## 결과

| 경우 | 기존 SQL 횟수 | 개선 SQL 횟수 | 기존 시간 | 개선 시간 |
| --- | ---: | ---: | ---: | ---: |
| 첫 기준값 저장 | 2,004 | 6 | 2,032.00ms | 92.75ms |
| 1,000게임 모두 증가 | 3,004 | 7 | 5,226.87ms | 230.32ms |
| 다음 관측에서 변화 없음 | 2,004 | 6 | 3,226.47ms | 47.67ms |

SQL 횟수에는 `BEGIN`, advisory lock, 수집 요청 확인, `COMMIT`도 포함된다. 개선 코드는 기존 기준값을 한 번에 읽고 증가분과 새 기준값을 각각 한 문장으로 저장한다. 변화가 없어도 마지막 관측 시각을 갱신해야 하므로 기준값 저장은 수행한다. 재실행 또는 오래된 관측은 기준값을 덮어쓰지 않는다. 모든 작업은 같은 트랜잭션에서 처리한다.

각 실행의 시간과 호출 수는 [원시 측정값](steam-collection-performance.json)에 남겼다. 통합 테스트는 1,000게임 저장의 최대 SQL 횟수, 증가분 수, 오래된 관측 무시, 잘못된 입력 거부를 계속 검증한다.

## 로그인 대기 개선

Discord 연결 목록 요청은 서버 멤버 확인과 함께 시작하되 그 완료를 기다리지 않는다. 사용자 권한과 세션을 반영한 뒤 [Next.js `after`](https://nextjs.org/docs/app/api-reference/functions/after)에서 계정 자동 연결을 완료한다. 연결 목록이나 Steam 프로필 조회 시간을 로그인 응답에 추가하지 않는다. 응답 후 작업도 함수 실행 시간 제한과 컴퓨팅 사용량의 영향을 받으며 별도 영속 작업 큐는 아니다. 실패한 연결은 다음 로그인에서 다시 시도한다.

로그인 통합 테스트에서는 연결 목록 응답을 보류한 상태에서 세션·권한·접속 기록이 만들어지는지 확인하고, 응답 후 작업을 실행하면 Steam 계정이 연결되는지 확인했다. 실제 Discord OAuth나 운영 Vercel에서 로그인 시간을 측정한 결과는 아니다. 자동 연결이 끝나기 전에 첫 화면이 열리면 새 계정은 새로고침 후 보일 수 있다.

## 적용 한계

이 측정은 같은 로컬 DB의 비교다. Neon의 절전 해제, 네트워크 왕복 시간, Vercel 동시 요청, Steam API 응답 시간과 호출 제한을 포함하지 않으며 운영 지연 시간 보장으로 사용하지 않는다. 측정 시간의 흔들림은 원시 값에서 확인할 수 있다. 확실히 확인한 변화는 게임 수에 비례하던 SQL 왕복을 최대 7회로 줄였다는 점이다. 쓰는 행 수와 장기 데이터 보존량 자체는 줄이지 않는다.

수집 작업은 여전히 계정별 7일 간격, 실행당 최대 20계정과 실행 시간 예산을 적용한다. 외부 API 조회 중에는 DB 연결을 보유하지 않고 계정을 순서대로 처리한다. 실제 운영에서 병목이 없다고 판단하려면 활성화 뒤 로그인 응답 시간·DB 컴퓨팅·수집 완료 및 이월 수를 관측해야 한다.
