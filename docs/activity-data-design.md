# 활동 데이터 수집 설계안

작성: 2026-10-09. 근거와 미확인 사항은 [activity-data-evidence.md](activity-data-evidence.md)에 분리한다. 이 문서는 구현 범위와 데이터의 의미를 정한다. 실제 운영 DB 용량과 정확한 Riot API 키 종류는 아직 확인하지 않았다. 사용자가 확인해 준 현재 Riot `Product Description`은 `personal study application`이며, 장기 경기 기록 기능은 설명에 드러나지 않는다.

## 목표와 원칙

- 나중에 **언제 누구와 어떤 게임을 했는지**, **게임 취향과 플레이 시간이 어떻게 바뀌었는지**, **Discord 활동이 시간에 따라 어떻게 변했는지** 답할 수 있는 사실을 남긴다. 화면과 공개 범위는 후속 작업이다.
- 월 5천~1만 건은 예상 부하를 검토할 때만 쓴다. 수집 성공의 기준은 행 수가 아니라 확인 가능한 활동의 포착률, 중복률, 결측 설명 가능성, 실제 활용 질문에 답할 수 있는지다.
- 외부 응답 전문을 장기 보관하지 않는다. 원본의 식별자와 시각, 필요한 최소 필드, 관측 출처를 구조화한다. 기존 캐시와 60일 Discord 메시지 보존은 그대로 둔다. 플랫폼의 삭제 요청과 API 사용 종료 시 해당 출처의 기록을 찾고 삭제할 수 있어야 한다.
- 사실의 시각을 구분한다. Riot 경기는 **경기 시각**, Discord 집계는 **활동 날짜**, Steam 변화는 **두 관측 사이의 구간**을 뜻한다. Steam 누적 시간 증가만으로 정확한 플레이 일시나 공동 플레이를 주장하지 않는다.
- 계정 소유자가 비어 있으면 사람을 추측해 연결하지 않는다. 사용자가 직접 남긴 기록이 생기면 외부 API 관측 사실과 출처를 구분한다.

| 나중에 답할 질문 | 필요한 관측 사실 | 이 데이터만으로 답할 수 없는 것 |
| --- | --- | --- |
| 언제 LoL을 함께 했나? | 같은 경기 ID의 등록된 PUUID와 팀, 경기 시각 | 등록되지 않은 친구의 신원, 누락된 경기의 참여 여부 |
| Steam 게임 취향이 어떻게 바뀌었나? | 계정 주인이 요청한 주기별 게임 누적 시간과 관측 구간 | 실제 접속 시각, 같은 시간에 함께 플레이했는지 |
| Discord 활동 흐름이 어떻게 변했나? | 수집 대상 범위의 날짜별 비식별 메시지·답글·반응 집계 | 특정 사람의 성격·관계·활동 이유 |

## 제안 데이터 모델

기존 마이그레이션을 수정하지 않고 다음 번호의 새 마이그레이션으로 추가한다. 필드명과 인덱스는 구현 때 쿼리 및 테스트로 확정한다.

### 1. Riot 경기

- `riot_account_identity`: 등록된 `members.id`와 PUUID의 대응, 마지막 확인 시각. 닉네임 변경과 동명이인을 구분한다. 소유자 연결은 기존 `owner_id`를 따른다.
- `riot_matches`: `match_id`를 기본키로 경기 시각, 큐/모드, 지속 시간, 관측 시각을 기록한다. 경기당 한 행이다.
- `riot_match_participants`: `(match_id, puuid)`를 고유키로 **등록된 멤버**의 팀, 챔피언, 승패와 필요한 최소 성과만 기록한다. 같은 경기의 등록 멤버를 조인해 공동 플레이를 도출한다. 상대·비등록 참가자의 닉네임과 상세 기록은 장기 저장하지 않는다.
- 경기 ID 목록을 멤버별로 페이지 단위 조회하고, 이미 처리한 경기와 겹칠 때까지 가져온다. 전역 최신 시각 하나에 의존하지 않는다. 경기 상세는 멤버 간 중복 ID를 제거해 한 번만 가져온다. 실패한 페이지나 429는 성공한 빈 목록으로 표시하지 않고 다음 실행에 재시도한다.
- 커스텀 경기 등 별도 공개 제한이 있는 큐는 저장·표시 정책을 공식 문서와 등록된 제품 범위에 맞춰 먼저 확인한다. **Riot 수집의 운영 활성화는 Developer Portal 제품 설명·심사 범위 확인 이후**로 둔다.

### 2. Steam 게임 시간

- `steam_collection_requests`: 계정 주인이 주기적 수집을 요청한 시각, 고지 버전, 중단 시각을 기록한다. 기존 관리자·타인 등록만으로 자동 수집을 켜지 않는다. 수집 요청·고지·저장 국가·삭제 흐름을 마련하기 전에는 Steam 장기 수집을 운영 활성화하지 않는다.
- `steam_game_totals`: `(steam_id, app_id)`별 마지막으로 **성공적으로 관측한** 누적 분과 관측 시각. 현재 기준값이다.
- `steam_playtime_changes`: 이전 관측 시각, 이번 관측 시각, 이전/이번 누적 분을 기록한다. 증가분은 두 누적값의 차이로 계산한다. 증가가 실제 관측된 게임만 추가한다. `(steam_id, app_id, 이번 관측 시각)`을 고유하게 해 재실행해도 중복되지 않게 한다.
- 주기적 수집을 명시적으로 요청한 계정만 주 1회 공개 보유 목록을 가져온다. 첫 관측은 기준값 생성이며 과거 플레이를 이 주의 활동으로 계산하지 않는다. 음수 변화는 활동 기록을 만들지 않고 다음 관측의 기준값만 갱신한다. 목록 누락은 무시하며, 비공개나 실패를 구별해 수집 상태에 기록하는 로직은 수집 작업을 연결할 때 추가한다.
- 소유 게임의 증감은 별도 확인이 가능할 때만 기록한다. 현재 `getLibrary`는 게임 목록이 없는 응답을 비공개와 구별하지 못하므로, 이 반환값만으로 제거 이벤트를 만들지 않는다.

### 3. Discord 활동 집계

- `discord_daily_activity`는 첫 단계로 구현한다. 한국 날짜별 메시지 수, 답글 수, 반응 수, 고유 작성자 **수**만 저장하며 사용자·채널 ID는 넣지 않는다. 전체 채널 동기화가 끝난 경우 원본 삭제 전 최근 60일을 다시 계산해 같은 날을 교체한다. Discord 정책상 이용자의 신원·관계 프로파일링을 피하기 위해 작성자별 장기 기록이나 관계 그래프는 새로 만들지 않는다.
- 기존 동기화가 최근 3일을 갱신하고 최대 8일까지 복구하므로 집계도 최근 보존 범위를 다시 계산해 `UPSERT`한다. 호출 제한·페이지 상한이 발생한 실행은 집계를 갱신하지 않고 부분 완료로 표시한다. 첫 배포 이전에 삭제된 원본은 복구할 수 없으며, 집계값도 관측 범위의 수치이지 완전한 Discord 활동의 증명은 아니다.
- 본문, 개별 메시지 목록, 임의의 감정·취향 해석은 장기 집계에 넣지 않는다. 기존 주간 칭호 같은 사용자 식별 기록의 범위를 확대하지 않는다. 장기 집계가 Discord 앱에 명시된 기능과 부합하는지도 활성화 전에 확인한다.

### 공통 수집 상태

- 기존 `ops_jobs`를 공통 실행 상태의 출발점으로 사용한다. 소스, 시작·종료 시각, 성공/부분/실패, 대상 수, 처리 수, 오류 **코드**를 기록하고, Riot·Steam 수집에 필요한 상태 필드만 다음 단계에서 확장한다. 비밀 값과 API 응답 본문은 넣지 않는다.
- 대상별 커서/최근 성공 범위를 두어, 한 멤버 또는 한 채널의 실패가 다른 대상의 진행 상태를 덮지 않게 한다. 실제 완료한 구간만 커밋한다.
- 저장된 사실에 `observed_at`과 출처를 보존한다. 수동으로 추가하는 플레이 기록이 나중에 필요해지면 `user_reported` 출처를 사용하고 Riot·Steam 관측과 섞지 않는다.

## 실행 구성

1. 현재 Vercel + Neon을 유지한다. 새로운 상시 서버나 데이터 웨어하우스는 추가하지 않는다.
2. 기존 Discord 일일 Cron과 분리된 **일일 수집 작업**을 설계한다. 그 안에서 Riot은 제품 심사 범위 확인 후 매일, Steam은 계정별 명시적 주기 수집 요청 후 주 1회 조건으로 처리한다. 각 작업은 호출·시간 예산과 대상별 재개 지점을 갖는다. 실제 `vercel.json` 변경 전에는 저장소의 사전 확인 규칙을 따른다.
3. 기존 Riot 프록시의 허용 경로와 비캐시 오류 규칙을 유지한다. 서버 수집이 동일한 프록시 경계를 재사용할지, 공통 Riot 클라이언트로 로직을 공유할지는 구현 전 호출 구조를 확인해 결정한다. 브라우저에 키를 노출하지 않는다.
4. 수집 실패를 조용히 빈 활동으로 바꾸지 않는다. 관리자 운영 상태에서 마지막 성공, 지연, 부분 완료, API 429/인증 오류를 구분한다.
5. 백업 파일은 암호화해 DB 외부에 보관하고 격리 DB로 정기 복구를 검증한다. R2는 이 흐름에 실제로 필요해질 때 도입한다. 현재 도구가 존재한다는 사실을 자동 백업 완료로 간주하지 않는다.

## 측정과 의사결정 기준

운영 DB와 Vercel 환경을 이 문서 작업에서 직접 조회·변경하지 않았다. 운영자는 관리자 화면과 Neon 콘솔의 수치를 함께 확인한다. 테이블별 기준값이 필요하면 읽기 전용 쿼리를 별도로 실행한다.

```sql
SELECT pg_size_pretty(pg_database_size(current_database())) AS database_size;

SELECT relname, pg_size_pretty(pg_total_relation_size(relid)) AS total_size,
       pg_total_relation_size(relid) AS total_bytes
FROM pg_catalog.pg_statio_user_tables
ORDER BY total_bytes DESC;
```

**300MB 목표 / 600MB 재검토 / 1GB 무료 한도**는 각각 자체 운영 목표, 구조 조정 신호, 제공사의 현재 한도로 구분한다. `pg_database_size`와 Neon의 프로젝트 사용량은 같은 지표라고 가정하지 않는다. 초기 2~4주 동안 소스별 행 수, 테이블·인덱스 바이트 증가량, 완전한 수집일 비율, 중복률, API 호출·429, 작업 시간, Neon 컴퓨팅 사용량을 재서 1년 예상치를 다시 계산한다. `1~2KB/기록`은 아직 측정되지 않은 가정이다.

## 구현 순서와 활성화 조건

1. **운영 기준선**: 실제 DB/Neon 사용량, 현재 키 종류와 Riot 등록 제품 설명, Discord 앱의 명시 기능, Steam의 계정 주인 요청·저장 고지·저장 국가, 백업·복구 현황 확인. 이 값이 없으면 용량과 지속 가능성을 확정하지 않는다.
2. **수집 골격**: 새 마이그레이션과 중복 방지 저장 로직을 구현했다. Riot·Steam의 실행 이력·대상별 재개 상태와 실제 수집 작업은 활성화 조건을 확인한 다음 단계다. 기존 마이그레이션과 인증·접근 제어는 수정하지 않는다.
3. **세 소스 수집**: Riot 경기, Steam 변화, Discord 일별 집계를 각각 작은 대상 집합으로 검증한다. 누락·재시도·비공개 계정·중복 실행을 테스트한다.
4. **운영 활성화**: Riot Developer Portal의 제품 범위와 기능 변경 심사, Steam의 계정별 수집 요청과 고지, Discord 정책 적합성, 삭제 절차, 자동 백업·복구 검증, Cron 설정 변경 사전 확인 후 배포한다. 최소 2~4주 관측 결과로 저장 주기·필드·보존 기간을 조정한다.
5. **활용 화면**: 데이터의 포착률과 실제 사용 질문이 확인된 뒤 별도 작업으로 만든다.

이 설계는 모든 친구가 공개 API에서 관측된다고 가정하지 않는다. 비공개 계정·키 만료·호출 제한·작업 누락이 생긴 구간은 `데이터 없음`으로 표시하고 `활동 없음`으로 해석하지 않는다.

### Riot 제품 설명 변경 초안

실제 제출 문구와 Riot의 심사 절차는 제품 소유자가 Developer Portal에서 확인한다. 다음은 기능을 숨기지 않고 설명하기 위한 초안이며, 제출·승인을 대신하지 않는다.

> Jaemangho is a private, non-commercial activity archive for a group of about 10–20 friends. With registered League of Legends accounts, it periodically retrieves completed match IDs and match details through the official Riot API. It stores the match ID, match time, mode, and minimal performance data for registered group members to preserve their play history and identify matches played together. It does not publish custom-match history without the required player permission, store full match responses long term, or sell the data.
